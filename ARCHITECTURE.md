# Архитектура Shelves

**Статус:** клиент подключён к Supabase Auth, Postgres и Storage. Разделы 1–11 описывают предшествовавший локальный прототип; актуальная схема и потоки данных приведены в разделе 12. Требования к поведению находятся в [PRD.md](./PRD.md), визуальные правила — в [DESIGN.md](./DESIGN.md).

## 1. Общая схема

Shelves — одностраничное приложение на React 19 и Vite 8. Серверной части, базы данных и внешнего книжного API нет. Все аккаунты, сессия, книги и полки хранятся в `localStorage` браузера.

```
src/main.jsx
  └── App.jsx
        ├── AuthPage.jsx   — если нет активной сессии
        └── Library        — если сессия есть
              ├── книги и полки текущего аккаунта
              └── модальные формы книги и полки
```

`App` хранит текущего пользователя в состоянии. При отсутствии пользователя показывается `AuthPage`, после входа — `Library` с ключом `user.id`, поэтому данные одного аккаунта не попадают в состояние другого.

## 3. Ключи `localStorage`

| Ключ | Формат | Назначение |
| --- | --- | --- |
| `shelves-auth-users-v1` | `Account[]` | Зарегистрированные локальные аккаунты. |
| `shelves-auth-session-v1` | `Session` | Активная сессия: только `id` пользователя. |
| `book-diary-v1` | `Book[]` | Книги тестового аккаунта. |
| `book-diary-shelves-v1` | `Shelf[]` | Полки тестового аккаунта. |
| `book-diary-folders-v1` | `Shelf[]` | Устаревший ключ полок; только для миграции. |
| `book-diary-<accountId>-books-v1` | `Book[]` | Книги зарегистрированного аккаунта. |
| `book-diary-<accountId>-shelves-v1` | `Shelf[]` | Полки зарегистрированного аккаунта. |

Тестовый аккаунт имеет фиксированный `id` `shelves-demo-account` и не записывается в `shelves-auth-users-v1`: его данные находятся в константе `DEMO_ACCOUNT` в `src/AuthPage.jsx`. Поэтому тестовый аккаунт использует общие ключи `book-diary-v1` и `book-diary-shelves-v1`, а зарегистрированные пользователи — ключи со своим `id`.

## 4. Схемы данных

### Account

```ts
type Account = {
  id: string;        // crypto.randomUUID()
  email: string;     // нижний регистр, уникальный
  password: string;  // открытый текст, только для демонстрации
};
```

Пример значения `shelves-auth-users-v1`:

```json
[
  {
    "id": "8f0c1d2e-4a5b-4c6d-8e7f-901234567890",
    "email": "reader@example.com",
    "password": "example-password"
  }
]
```

### Session

```ts
type Session = {
  id: string; // id аккаунта или shelves-demo-account
};
```

Пример значения `shelves-auth-session-v1`:

```json
{ "id": "shelves-demo-account" }
```

Если ключ отсутствует или JSON повреждён, активной сессии нет. Для зарегистрированного аккаунта при загрузке выполняется поиск по `id` в `shelves-auth-users-v1`; если аккаунт не найден, сессия считается недействительной.

### Book

```ts
type BookStatus = 'reading' | 'planned' | 'read' | 'paused';

type Book = {
  id: string;          // crypto.randomUUID()
  title: string;       // обрезанные пробелы, обязательное
  author: string;      // обрезанные пробелы, обязательное
  status: BookStatus;  // по умолчанию reading
  shelfId: string;     // '' или Shelf.id
  rating: number | ''; // 1–5 или '' 
  impression: string;  // может быть пустым
  startedAt: string;   // YYYY-MM-DD или ''
  finishedAt: string;  // YYYY-MM-DD или ''
  addedAt: string;     // ISO-время; у старых записей может быть ''
  coverImage: string;  // JPEG data URL или ''
};
```

Соответствие статусов:

| Значение | Подпись | Оценка | `startedAt` | `finishedAt` |
| --- | --- | --- | --- | --- |
| `reading` | Читаю | 1–5 или пусто | Необязательно | Всегда пусто |
| `planned` | В планах | Всегда пусто | Всегда пусто | Всегда пусто |
| `read` | Прочитано | 1–5 или пусто | Необязательно | Дата или текущая дата |
| `paused` | Отложено | 1–5 или пусто | Всегда пусто | Всегда пусто |

### Shelf

```ts
type Shelf = {
  id: string;   // crypto.randomUUID()
  name: string; // обрезанные пробелы, уникальное без учёта регистра
};
```

Связь книги с полкой хранится только в `Book.shelfId`. Отдельного списка книг у полки нет: он вычисляется фильтрацией книг по `shelfId`. Если полка удалена, у её книг устанавливается `shelfId: ''`.

## 5. Инварианты и правила

- Почта при регистрации и входе приводится к нижнему регистру; повторная регистрация адреса, включая адрес тестового аккаунта, запрещена.
- Пароль при регистрации содержит не менее 8 символов. При входе длина не проверяется: пароль должен совпасть с сохранённым.
- `title` и `author` не могут быть пустыми после обрезки пробелов.
- `shelfId` либо пуст, либо ссылается на существующую полку текущего аккаунта.
- Названия полок уникальны без учёта регистра в пределах аккаунта.
- `rating` хранится числом от 1 до 5 или пустой строкой; для `planned` всегда пустая строка.
- `startedAt` сохраняется только для `reading` и `read`; `finishedAt` — только для `read`.
- При переводе в `read` без указанной даты подставляется текущая локальная дата.
- При редактировании книги сохраняются её `id`, `addedAt` и `coverImage`.
- Фотография обложки сжимается в браузере до JPEG не больше 420×630 px с качеством 0.78 и хранится как data URL. В CSV фотографии не попадают.
- Все записи одного аккаунта находятся только в его ключах `localStorage`; демо-аккаунт использует общие ключи `book-diary-*`.

## 6. Потоки данных

### Загрузка приложения

1. `App` вызывает `getCurrentUser()`.
2. `getCurrentUser()` читает `shelves-auth-session-v1`.
3. Если `id` равен `shelves-demo-account`, возвращается `DEMO_ACCOUNT`.
4. Иначе аккаунт ищется в `shelves-auth-users-v1` по `id`.
5. Без пользователя показывается `AuthPage`; с пользователем — `Library`.

### Вход

1. Почта обрезается и приводится к нижнему регистру.
2. Проверяются заполненность полей и формат почты.
3. Для адреса тестового аккаунта пароль сравнивается с константой.
4. Для остальных адресов аккаунт ищется по совпадению `email` и `password`.
5. В `shelves-auth-session-v1` записывается `{ "id": "<accountId>" }`.

### Регистрация

1. Проверяются формат почты, пароль от 8 символов и отсутствие дубликата.
2. Создаётся `Account` с `crypto.randomUUID()`.
3. Массив аккаунтов записывается в `shelves-auth-users-v1`.
4. Сразу создаётся сессия.

### Работа с каталогом

1. `Library` выбирает ключи книг и полок по `user.id`.
2. Начальные значения читаются из `localStorage`; для демо-аккаунта выполняется миграция полок.
3. Изменения состояния книг и полок автоматически записываются в соответствующие ключи через `useEffect`.
4. Выход удаляет только `shelves-auth-session-v1`; аккаунты и данные остаются.

## 7. Миграции и совместимость

- Если `book-diary-shelves-v1` отсутствует, но есть `book-diary-folders-v1`, массив полок копируется в новый ключ. Старый ключ не удаляется и остаётся резервной копией.
- При чтении книги поле `folderId` преобразуется в `shelfId`. Если `shelfId` уже есть, оно имеет приоритет.
- Миграция выполняется при входе под тестовым аккаунтом; для зарегистрированных аккаунтов исторические ключи не используются.
- Формат ключей версионирован суффиксом `-v1`. При несовместимом изменении схемы нужно добавить новый суффикс и чтение старых данных с преобразованием, не удаляя пользовательские записи.

## 8. CSV-экспорт

Колонки: `ID`, `Название`, `Автор`, `Статус`, `Оценка`, `Впечатление`, `Полка`, `Начало чтения`, `Дата прочтения`, `Дата добавления`.

Файл формируется в UTF-8 с BOM, разделитель — запятая, перевод строки — CRLF, имя — `shelves-books-YYYY-MM-DD.csv`. Фотографии обложек не экспортируются.

## 9. Ограничения

- Пароли хранятся в открытом виде в `localStorage` и доступны любому скрипту на странице. Это демонстрационный прототип, а не production-авторизация.
- Данные привязаны к браузеру и устройству; синхронизации и восстановления нет.
- Очистка данных браузера удаляет аккаунты, книги, полки и обложки.
- Большие фотографии обложек занимают место в `localStorage` и могут приблизить исчерпание квоты.
- Автоматические тесты не настроены; изменения проверяются вручную по [PRD.md](./PRD.md).

## 10. Как проверить структуру

1. Открыть приложение и войти под нужным аккаунтом.
2. Открыть DevTools → **Application → Local Storage → адрес приложения**.
3. Проверить ключи из раздела 3 и JSON-форматы из раздела 4.
4. Для проверки миграции использовать тестовый аккаунт с существующим `book-diary-folders-v1` и полем `folderId` в книгах.

## 11. Правило изменения схемы

Перед изменением полей, ключей или форматов:

1. Описать новую схему в этом файле.
2. Предусмотреть чтение и преобразование старых данных.
3. Не удалять и не перезаписывать пользовательские ключи без резервной копии.
4. Обновить требования и проверки в [PRD.md](./PRD.md).
5. Проверить вход, сохранение после перезагрузки и разделение данных аккаунтов.

## 12. Текущая архитектура Supabase

**Статус раздела:** подключение реализовано в клиенте. Схема Supabase находится в `supabase/migrations/0001_init.sql`, `0002_profiles.sql` и `0003_profiles_without_username.sql`.

### Регистрация и вход

- Регистрация принимает только email и пароль; отдельного логина или имени пользователя нет.
- Аккаунт и пароль создаёт и проверяет Supabase Auth. При выключенном `Confirm email` успешный `signUp` сразу возвращает сессию; email автоматически считается подтверждённым, но Supabase не проверяет, что пользователь владеет этим адресом.
- Профиль без дополнительных пользовательских полей хранится в `public.profiles` и связан с `auth.users` по `user_id`. Профиль создаётся автоматически при создании пользователя.
- Пароль не копируется в `profiles` или пользовательские таблицы.
- Вход, выход и обновление сессии выполняются через Supabase Auth. Демо-вход также обращается к Supabase Auth; тестовый пользователь должен быть создан в Auth.

### Восстановление пароля и Google OAuth

- `src/AuthPage.jsx` запрашивает письмо через `resetPasswordForEmail` с возвратом на `${window.location.origin}/reset-password`. Ответ об отправке не раскрывает наличие аккаунта. Успешная регистрация по email по-прежнему не требует подтверждения почты.
- `src/App.jsx` обрабатывает `PASSWORD_RECOVERY` отдельно от обычного входа. Путь `/reset-password` сохраняет форму при перезагрузке; без сессии или при ошибке callback показывается запрос нового письма. Маркер `retry=1` открывает повторный запрос даже при существующей сессии.
- `src/ResetPasswordPage.jsx` проверяет длину и совпадение паролей, затем вызывает `updateUser({ password })`. Успех отображается только после ответа Auth. В клиентских таблицах пароли не сохраняются.
- `src/lib/auth.js` содержит общие правила полей, адреса возврата, чтение состояния callback до обработки SDK и сообщения ошибок. Callback очищается из адресной строки после чтения сессии.
- Вход Google запускается через `signInWithOAuth({ provider: 'google' })`. Используется текущий браузерный implicit flow Supabase (`detectSessionInUrl: true`); SDK читает возвращённую сессию. Клиент предварительно проверяет публичный `/auth/v1/settings`, чтобы отключённый провайдер не уводил пользователя на страницу ошибки.
- Google Client ID/Secret настраиваются только в Supabase provider settings. Новая учётная запись использует существующий триггер создания профиля, книги и RLS связаны с тем же `auth.users.id`. Связыванием идентичностей управляет Supabase Auth; приложение не объединяет записи по email.
- Дополнительные SQL-миграции и переменные окружения для этих сценариев не нужны. Для отправки писем обычным пользователям требуется SMTP; для Google — настроенный OAuth-клиент и разрешённые URL возврата. Пошаговая настройка находится в `supabase/README.md`.

### Облачные данные

Существующая миграция `supabase/migrations/0001_init.sql` задаёт таблицы `books` и `shelves`, ограничения статусов и оценок, RLS-политики и приватный bucket `book-covers`. Целевой набор данных:

| Набор | Хранение | Доступ |
| --- | --- | --- |
| Учётная запись и пароль | Supabase Auth (`auth.users`) | Создание/вход/выход через Auth API; приложение не читает и не меняет таблицу напрямую. |
| Профиль | `public.profiles` с `user_id` и системными датами | Профиль создаётся триггером; строки закрыты RLS. |
| Книги | `public.books`: владелец, полка, название, автор, статус, оценка, впечатление, даты, дата добавления и `cover_path` | Только владелец строки читает, добавляет, редактирует и удаляет её. |
| Полки | `public.shelves`: владелец, название и системные даты | Только владелец строки читает, добавляет, переименовывает и удаляет её. Удаление полки оставляет книгу в каталоге без полки. |
| Фото обложек | Объекты приватного bucket `book-covers`; в `books` хранится только путь | Вошедший владелец может читать/загружать/заменять/удалять только объекты в каталоге со своим `user_id`. |

Все прикладные таблицы закрыть RLS-политиками для роли `authenticated`: `user_id = auth.uid()` для чтения, создания, изменения и удаления; для книги дополнительно проверять, что указанная полка принадлежит этому же пользователю. Storage остаётся приватным, публичные URL не использовать. В браузере разрешён только публичный anon/publishable key; `service_role` ключ не включать в клиент и не коммитить.

Фильтры, выбранная полка и сортировка остаются временным состоянием интерфейса, пока отдельное требование не предусматривает синхронизацию настроек. CSV строится из полученных книг и названий полок, фотографии в него не включаются.

Цвет обложки по-прежнему вычисляется из UUID книги функцией `coverColorIndex`; прежнее соответствие сохраняется, включая два старых индекса индиго (0 и 5). При создании `createBookId` выбирает следующий из пяти цветов после книги с самым поздним `addedAt` во всём загруженном каталоге и генерирует случайный UUID с соответствующим индексом цвета 0–4. Это сохраняет цвет на разных устройствах без нового поля или SQL-миграции. При редактировании UUID не меняется. Одновременное добавление с разных устройств может выбрать одинаковый следующий цвет, поскольку цикл определяется загруженным каталогом.

### Локальные данные и перенос

Старая локальная модель описана в разделах 1–11 и может служить источником для будущего переноса. Текущий клиент не читает её и не выполняет автоматический импорт. До отдельной миграции старые ключи `localStorage` остаются нетронутыми; новые записи сохраняются в Supabase.

### Настройка и внедрение

**Владелец проекта в Supabase:** создаёт проект и выбирает регион; включает Email provider, разрешает регистрацию и выключает Confirm email; указывает Site URL и Redirect URLs; задаёт минимальную длину пароля; применяет миграцию базы и политик; проверяет приватность bucket и ограничения размера/MIME; передаёт приложению Project URL и anon/publishable key через переменные окружения. Секретный `service_role` остаётся только вне клиентского приложения.

**Подключено в коде:** SDK-клиент читает `.env.local`; вход и регистрация идут через Supabase Auth; профиль создаётся триггером; CRUD книг и полок работает через Postgres; фото загружаются в Storage; русский интерфейс, статусы, правила дат и CSV-экспорт сохранены. Автоматический перенос старых локальных данных пока не реализован.

**Проверка:** регистрация содержит только email и пароль; при выключенном подтверждении email сразу открывает каталог; повторный email отклоняется; профиль автоматически появляется в `public.profiles`; книги, полки и обложки недоступны другим пользователям; чужую полку нельзя назначить книге; ограничения статусов сохраняются; CSV содержит метаданные без фото.

### Конфигурация и ограничения

- Корневой `.env.local` содержит `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`; он игнорируется Git. Шаблон без реальных значений находится в `.env.example`.
- `src/lib/supabase.js` читает переменные и создаёт клиент. После изменения `.env.local` Vite нужно перезапустить.
- Регистрация не передаёт пользовательские метаданные. Триггер `create_profile_for_new_user` создаёт профиль только с ID пользователя.
- Секретный `service_role` key в клиенте не используется.
- Регистрация без подтверждения email зависит от настройки **Confirm email** в Supabase Dashboard.
- Публичные запросы к таблицам закрыты; строки доступны аутентифицированному владельцу через RLS. Приватные изображения выдаются по временным signed URL.
- Локальный каталог автоматически не переносится; старые локальные пароли не используются приложением.
